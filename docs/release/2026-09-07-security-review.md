## Critical/high priorities

### 1. Critical, confirmed metadata — profiles bypass task authorization, including after proposal 014 alone

- **Evidence:** `db/proposals/014_profiles_rls.up.sql:5` records July 30 RLS OFF with broad anon/authenticated grants. `supabase/schema_backup_20260730_185314.sql:6801` grants authenticated users all task operations when their `profiles.role = 'admin'`. Own-profile INSERT/UPDATE policies at `:6866` and `:6893` only check `id = auth.uid()`. The role is a mutable text column at `:4394`; no profile protection trigger is present in the saved trigger inventory. `db/proposals/012_create_update_task_rpcs.up.sql:152` explicitly preserves the admin policy.
- **Impact:** Current metadata confirms anonymous profile writes are permitted while RLS is off. Enabling RLS alone leaves the own-role escalation path to the task admin policy. The authorization consequence is inferred from verified grants/policy definitions; no malicious write was executed.
- **Fix:** First inspect live RLS, table/column grants, policies and profile triggers. Prepare a reviewed migration that enables RLS and removes the unsupported task admin bypass, or moves administrator authorization to server-owned data. Prevent client INSERT and UPDATE of privileged profile fields. Check bootstrap/upsert compatibility before restricting columns.
- **Verification:** In an isolated database, prove own display-name/appearance updates succeed; assigning an admin role fails; changing another profile fails; stranger task reads/writes fail; authorized lifecycle RPCs still work. No destructive production probe is needed.
- **Correction:** Proposal 014 at `:55` and its validation comments incorrectly imply RLS protects retained TRUNCATE grants. Whole-table TRUNCATE is outside RLS. Revoke unnecessary grants in the reviewed hardening proposal; this is not evidence that PostgREST exposes a TRUNCATE endpoint. [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

### 2. High, confirmed metadata — legacy permissive Storage policies defeat the narrower policies

- **Evidence:** Saved schema `:7010` allows any authenticated proof upload; `:7017` grants anon proof reads; `:7024` allows all Storage reads to authenticated/anon; `:7045`, `:7052`, `:7059` allow any authenticated caller to delete/insert/update reward images. The live snapshot confirms these policies remain. The canonical migration `supabase/migrations/20260611120000_storage_buckets_and_policies.sql:41` only replaces its own named policies and leaves those legacy names untouched.
- **Impact:** Private proofs may be readable by outsiders through authenticated/signed Storage APIs, and another user's reward images may be overwritten/deleted. A private bucket flag and a correct narrow policy do not establish effective isolation.
- **Fix:** Inventory every current `storage.objects` policy, not only the intended ones. Stage removal of overlapping broad policies, retaining exactly the necessary per-bucket rules. Verify all bucket privacy, MIME and size settings live.
- **Verification:** Test owner, mission recipient, unrelated authenticated user and anon across list, signed URL, read, upload, overwrite and delete. Existing `src/security/storagePolicies.test.ts:31` checks only that expected text exists in one migration; it cannot catch additional live policies.
- **Why:** Default permissive PostgreSQL policies combine with OR, so a permissive legacy rule still grants access even when a stricter rule also exists. [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

### 3. High — server boundaries do not yet enforce the private People model

- **Evidence:** Applied proposal `db/proposals/013_standing_self_assign.up.sql:50` through `:78` accepts any existing `p_assigned_to`, with no accepted-connection check. Its `update_task` replaces the assignee at `:147` and `:163` without a connection check. Saved friendship INSERT policy `supabase/schema_backup_20260730_185314.sql:6810` checks only `requested_by = auth.uid()`; UPDATE at `:6845` allows either endpoint to update any permitted columns. No state-transition trigger is in the saved trigger inventory.
- **Impact:** Authenticated callers can send missions to arbitrary account IDs. If friendship policy state is unchanged, they can directly create an accepted friendship or accept their own request, defeating consent and future block checks. UI recipient filtering is not authorization.
- **Fix:** Introduce server-authoritative request/accept/reject/remove operations; make endpoint IDs immutable, validate transitions and require the recipient to accept. Add bilateral block checks to invitation redemption, friendship creation and mission/reward assignment. Keep existing accepted missions accessible as intended when a connection is removed; explicitly define the behavior of a durable block.
- **Related correctness gap:** Saved DELETE policy at `:6859` only permits the sender to delete their own pending request. `src/hooks/useFriends.ts:285` and `:329` attempt recipient rejection and accepted-friend removal, then report success without checking affected rows. Current live behavior needs verification.
- **Verification:** Test actor matrix (sender/recipient/stranger), self-acceptance, forged accepted inserts, pair rewrites, repeated requests, removal, blocked re-invites and direct assignment outside the People list.

### 4. Account deletion — implemented and tested locally; deployment remains gated

The initial audit found no deletion endpoint and non-cascading dependencies that made a direct Auth delete unsafe. That source gap is now addressed by `supabase/functions/delete-account/handler.ts:62`, `src/lib/accountDeletion.ts:28`, the flag-gated Profile panel, and staged proposal `db/proposals/018_account_deletion.up.sql:197`. The public destructive request accepts no caller target; it verifies Auth and binds the exact token's session to `auth.sessions.user_id`, fresh `created_at` and non-expired `not_after`. A refreshed JWT timestamp is insufficient. A separate opaque read-only receipt can confirm actual completion without relying on refresh after Auth removal.

`018_account_deletion.up.sql:227` inventories owned objects and canonical avatars/reward images/shared mission proofs, including uppercase UUID segments. The handler removes actual objects through Storage APIs before transactional relational cleanup (`:248`), then deletes Auth and verifies absence. Other people's credit amounts/balances remain; references to deleted missions are cleared. Other people's offers assigned to the departing account stay creator-private, become inactive and lose that assignment. Proposal 017 also repairs the previously missing purchase recipient check: SELECT RLS alone could not protect a known reward UUID from the SECURITY DEFINER purchase RPC.

`018_account_deletion.up.sql:35` uses a VOLATILE liveness guard plus advisory locks. Client and ordinary service writes cannot recreate frozen links/objects; only controlled cleanup can detach them. Strict table/FK, reward policy and audited purchase-definition checks abort schema drift before Storage work. A service-only progress marker allows deterministic partial retries, and success requires actual Auth absence. All this remains staged: no live account, data or file was deleted.

Verification: 29 behavioral endpoint/helper tests and 38 disposable PostgreSQL checks pass. The SQL fixture uses the saved complete public table definitions and confirmed live FKs/policies, applies 016/017/018, tests shared deletion/retained credits, stale/revoked sessions, service-owned and uppercase paths, schema drift, and two real concurrent database sessions in both lock orderings. These tests do not prove hosted Storage byte removal, actual Auth refresh invalidation or iPhone behavior. The [018 runbook](../runbooks/PROD_RUNBOOK_018.md) keeps `VITE_ACCOUNT_DELETION_ENABLED` off until reviewed deployment and hosted tests, and records the remaining receipt retention/support recovery work. [Supabase sessions](https://supabase.com/docs/guides/auth/sessions), [Auth/Storage deletion constraints](https://supabase.com/docs/guides/auth/managing-user-data), [Storage object deletion](https://supabase.com/docs/guides/storage/management/delete-objects).

## Medium priorities

### 5. Public profile reads include email addresses

`supabase/schema_backup_20260730_185314.sql:4388` places email in profiles; the SELECT policy at `:6838` is public `USING (true)`. Proposal 014 deliberately retains public reads (`db/proposals/014_profiles_rls.up.sql:43`). The live snapshot confirms anon/authenticated SELECT on email, so the public API permits email enumeration. Public display names do not require public email access. Keep emails self-only/server-only; replace the existing profile search with a bounded authenticated lookup that reveals only necessary display data. Review all joins and bootstrap reads before changing grants.

### 6. Reward email — hardened locally; durable delivery still outstanding

The old endpoint trusted editable `profiles.email`, replayed every qualifying purchase, and returned raw provider/database errors. The new `supabase/functions/notify-reward-creator/handler.ts` verifies the bearer token, binds the collector, looks up the actual collection and creator, and obtains the confirmed recipient from Auth admin `getUserById`. Generic email content eliminates user-text HTML interpolation and avoids exposing reward text in inbox previews. Profile lookup is no longer needed. [Supabase Auth admin lookup](https://supabase.com/docs/reference/javascript/auth-admin-getuserbyid).

POST/JSON/UUID validation, a 1 KB streamed body limit, a server-event age limit of one hour, a ten-second provider timeout, generic errors and a stable `reward-collected/{collection_id}` provider key bound this immediate-send path. Resend retains idempotency keys for 24 hours; the shorter event window prevents sending old collections after that retention expires, assuming the server-generated timestamp remains authoritative. This is **not a durable outbox, cross-event rate limit or delivery guarantee**. Deploy only after database authorization is repaired and service configuration is verified. [Resend idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys).

The concrete next design is [reward-notification-delivery-proposal.md](reward-notification-delivery-proposal.md). No provider request was sent during implementation; fetch was mocked. Existing legacy alert functions remain fail-closed stubs in source. Authenticated CLI inventory confirms that no Edge Functions, including this notifier, are currently deployed; email availability is absent, not verified delivery.
